# libazahar-py v1.3.0

A headless, scriptable host for Azahar's 3DS libretro core, with a Python layer, for testing homebrew, on macOS
(Apple silicon, macOS 15 or later) and Windows x64. This release is for people outside this repository: the host comes
prebuilt (no compiler needed), a recipe runs your own homebrew app in GitHub Actions, and a gymnasium-style example
shows a learning loop. The cores are the same as v1.2.0's. The 1.0 promise (semantic versioning: until 2.0, the Python
API, the C functions in `host/azhost.h`, the `azhost` command line and exit codes, and the input-script and
option-profile formats change only in compatible ways) holds on both systems. `STATUS.md` in the repository says what
works and what does not, each item with the work that proved it.

this project is not affiliated with Nintendo.

## What is new

- The host, prebuilt: `libazahar-py-host-1.3.0-macos-arm64.zip` and `libazahar-py-host-1.3.0-windows-x64.zip` hold
  `libazhost` and `azhost`, built by this repository's `host-bin.yml` workflow from the commit their `SOURCE.md` names.
  `sh tools/fetch.sh --host` downloads the one for your system, checks it against its sha256 pin and puts the two files
  in `build/`. With `--lazpy-core --testapp` (and `--moltenvk` on macOS) you need no compiler and no `make`, only
  `git`, `curl`, `unzip` and Python 3.10 or newer (the README's "No compiler" section).
- Running your own app in CI: `examples/ci/macos.yml` is a GitHub Actions workflow for a hosted macOS runner, and
  `docs/CI.md` walks through it. It fetches the prebuilt host and core and runs your copy of `examples/verdict.py` on
  your app. Best effort: a hosted runner may have no usable Vulkan path, so the job is set to continue-on-error and you
  read its verdict step.
- `examples/gym_env.py`: a gymnasium-style environment over the test app (the top screen as the observation, a reward
  read with `emu.memory`, `reset` loads a state). Outside the promise; it needs `pip install gymnasium` and our core.
- The state-boot time bound in our own tests only records the time on a GitHub-hosted runner, where a shared machine
  made it fail at v1.1.0 and v1.2.0; off a hosted runner it is still a gate.
- Windows emulator CI: `test-windows-live.yml` runs the slow tests (they boot the emulator) on a hosted Windows runner
  on lavapipe, a software Vulkan driver (MSYS2's Mesa, pinned by sha256 in `tools/fetch-mesa.sh`). One test is left out
  there: on lavapipe the depth of cleared pixels reads back other than the clear value (the stencil counts match); it
  runs on the PC's GPU and in the macOS CI. Best effort, like the recipe.
- Version 1.3.0 in `pyproject.toml` and `libazahar.__version__`.

## Upgrading

Nothing to change. The cores, the test app, the API and the formats are as in v1.2.0, so v1.2.0 states load. A host
you build with `make` still works; a plain `fetch.sh --host` replaces it with the release's.

## Windows

- Proven on one PC only: Windows 10 Pro 22H2, x64, an NVIDIA GeForce RTX 3060, driver 610.88, Python 3.10.11.
- CI adds Windows Server 2025 for the build, the fast tests and the core load test.
- CI also runs the emulator tests there on lavapipe (best effort; one test left out, above).
- Windows 11 and AMD and Intel GPUs are untested.
- No Windows speed figures. The instance cap stays 4.
- A GPU driver with Vulkan is required; no Vulkan is shipped.
- On the PC above, fresh clones of the release candidate passed the full suite from the staged files by both routes,
  the build route and the no-compiler one (441 passed, 13 skipped, each by design, 1 expected failure; the two 3-copy
  `Pool` tests left out on that 2-copy PC). The no-compiler run shows that no build step runs; that PC still has a
  compiler installed.
- The Windows core is v1.2.0's build, the same DLL bytes. Its zip has other bytes: its `SOURCE.md` names this
  release's assets. `SHA256SUMS` and `tools/fetch.sh` pin this one.

## macOS

The macOS core is unchanged since v1.0.0. On the release candidate (commit db83f99) the hosted CI jobs passed: the fast tests on Python 3.10 and 3.14 (356
passed, 9 skipped each, `test.yml` run 44803599115), and the emulator suite (`macos-live.yml` run 44803605270) had 432
passed, 25 skipped and 0 failed, with the state-boot bound only recording its time on that shared runner; the
recipe's run-and-verdict part printed `verdict ok` on our test app. The skips are Windows-only tests, the comparisons
with Azahar's own core (not given to that job), four inputs that job lacks (a release fixture, the test app's ELF, two
older cores), and the two audio tests (CI has no tone test app). That job builds the host with `make`; the macOS host
zip was built and signed in `host-bin.yml`. The no-compiler route on macOS has not run yet: it can run only from the
published release (a hosted runner fetches the zip from the release page); `STATUS.md` will record the result.

## Assets

Inherited from v1.0.0, the same bytes (the macOS core and its source):
- `azahar_lazpy_libretro-2126.2-lazpy.2-macos-arm64.zip`: our macOS core.
- `libazahar-py-core-build-v1.0.0.tar.gz`: the patches, pins, options and build script for the macOS core.
- `azahar-unified-source-2126.2-lazpy-nokeys.tar.xz`: the Azahar source both cores were built from.
- `openssl-3.6.5.tar.gz`: OpenSSL's source tarball.
- `citra_system_archives-f470e0c.tar.gz`: the generator snapshot behind the system archives in the cores.
- `testapp.3dsx`: the small homebrew test app used by the tests.
- `NOTICES.md`: the macOS licence notices.

The Windows core, as in v1.2.0:
- `azahar_lazpy_libretro-2126.2-lazpy.2-windows-x64.zip`: our Windows core (v1.2.0's DLL), with `NOTICES.md`,
  `SOURCE.md`, `LICENSE`, `COPYING-azahar.txt` and `build.inputs`.
- `NOTICES-windows-x64.md`: the Windows zip's notices, also as a plain file.
- `libazahar-py-core-build-v1.3.0.tar.gz`: the build files for the Windows core (the same files as v1.2.0's).
- `mingw-w64-runtime-source.tar`: the source of the compiler runtime parts linked into the Windows core.

New in v1.3.0:
- `libazahar-py-host-1.3.0-macos-arm64.zip`: `libazhost.dylib` and `azhost` (signed ad hoc), `LICENSE` and `SOURCE.md`.
- `libazahar-py-host-1.3.0-windows-x64.zip`: `libazhost.dll` and `azhost.exe`, `NOTICES.md` (the compiler runtime parts
  linked in), `LICENSE` and `SOURCE.md`.

And `SOURCE.md` (maps each binary to its source) and `SHA256SUMS` (sha256 of every other asset).

## Licence and source

Our binaries (both cores, the two host zips and the test app) are GPLv3; the third-party source assets keep their
own licences. The cores' complete corresponding source is on this page: the Azahar source asset, the
OpenSSL source tarball, the system-archive generator snapshot, both build-files assets, the compiler runtime source, and
this repository at the tag. The host's source is this repository at the commit its zip's `SOURCE.md` names (`host/`
and the `Makefile`). The Windows core links OpenSSL (Apache-2.0) statically; runtime parts keep their own licences,
listed in `NOTICES-windows-x64.md` and in the Windows host zip's `NOTICES.md`.

## Homebrew only

Homebrew only: no ROMs, no console keys, no Nintendo certificates and no Nintendo system files are included or needed by the tests; our core is built
without Azahar's built-in key data and default HTTP client certificate, and it loads no keys.

## Install

See the README, which has macOS and Windows steps, with and without a compiler. On macOS, macOS 15 or later is required.
