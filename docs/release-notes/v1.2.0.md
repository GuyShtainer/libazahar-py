# libazahar-py v1.2.0

A headless, scriptable host for Azahar's 3DS libretro core, with a Python layer, for testing homebrew, on macOS
(Apple silicon, macOS 15 or later) and Windows x64. This release adds a command line, audio capture, image compare with
a pass/fail example, errors that name their log, and a guest clock that no longer depends on the host's time zone. The
1.0 promise (semantic versioning: until 2.0, the Python API, the C functions in `host/azhost.h`, the `azhost` command
line and exit codes, and the input-script and option-profile formats change only in compatible ways) holds on both
systems. `STATUS.md` in the repository says what works and what does not, each item with the work that proved it.

this project is not affiliated with Nintendo.

## What is new

- A command line: `python -m libazahar doctor` checks the setup, `python -m libazahar run` runs an app with inputs
  and shots (`docs/USING.md` section 2a).
- Audio capture: `run(..., audio=True)` gives the batch's samples as int16 stereo and the rate (USING section 12b).
  Playback is still not supported.
- `images.compare` with pixel limits, the pass/fail example `examples/verdict.py`, and one exit-code table (USING
  section 3).
- Errors carry `.workdir` and `.log_path`, and their message names the log and the newest screenshot.
- What repeats run to run is written down (USING section 10a) and tested, with `images.digest`.
- The guest clock no longer depends on the host's time zone: the worker runs in UTC, so on our core one tick seed gives
  one clock on every machine (USING section 10a). The fixed start time in the option profile moved by two hours to
  keep the guest's clock where it was on the machine the earlier tests ran on.
- The same button pressed twice registers twice when it is released for one frame between.
- A worker ends when the script that started it dies: a kill-on-close Job object on Windows, a kqueue watch on macOS.
- `Pool` with two live copies; no window opens on Windows (checked by a window watch during a full run).
- The release check prints SKIP or PEND, not PASS, for a check that could not run.
- A rebuilt Windows core: OpenSSL's folders are compiled in at their Windows defaults (`C:/Program Files/Common
  Files/SSL` and `C:/Program Files/OpenSSL/lib/...`) instead of paths inside the build's own prefix. The same Azahar
  source and patches as v1.1.0's Windows core. The macOS core is unchanged since v1.0.0.
- Version 1.2.0 in `pyproject.toml` and `libazahar.__version__`.

## Upgrading

- A savestate made with the v1.1.0 Windows core may not load with v1.2.0's: make new states. macOS states are not
  affected (the same core).
- Runs that read the guest clock under the option profile's fixed start time: on a host in UTC or west of it,
  v1.1.0's guest clock stuck at 2000-01-01 00:00:00 (the core clamps a start before it); v1.2.0's starts about an hour
  past it on every machine (USING section 10a).

## Windows

- Proven on one PC only: Windows 10 Pro 22H2, x64, an NVIDIA GeForce RTX 3060, driver 610.88, Python 3.10.11.
- CI adds Windows Server 2025 for the build, the fast tests and the core load test.
- Windows 11 and AMD and Intel GPUs are untested.
- No Windows speed figures. The instance cap stays 4.
- A GPU driver with Vulkan is required; no Vulkan is shipped.
- Savestates do not carry between macOS and Windows, as in v1.1.0. `docs/USING.md` section 15a has every difference.

## macOS

The v1.2.0 changes were built and tested on the Windows PC. On macOS they ran in the hosted CI jobs on the release
candidate: TO BE FILLED from the candidate's `test.yml` and `macos-live.yml` runs.

## Assets

Inherited from v1.0.0, the same bytes (the macOS core and its source):
- `azahar_lazpy_libretro-2126.2-lazpy.2-macos-arm64.zip`: our macOS core.
- `libazahar-py-core-build-v1.0.0.tar.gz`: the patches, pins, options and build script for the macOS core.
- `azahar-unified-source-2126.2-lazpy-nokeys.tar.xz`: the Azahar source both cores were built from.
- `openssl-3.6.5.tar.gz`: OpenSSL's source tarball.
- `citra_system_archives-f470e0c.tar.gz`: the generator snapshot behind the system archives in the core.
- `testapp.3dsx`: the small homebrew test app used by the tests.
- `NOTICES.md`: the macOS licence notices.

New in v1.2.0:
- `azahar_lazpy_libretro-2126.2-lazpy.2-windows-x64.zip`: our rebuilt Windows core, with `NOTICES.md`, `SOURCE.md`,
  `LICENSE`, `COPYING-azahar.txt` and `build.inputs`. The same file name as v1.1.0's, other bytes: `SHA256SUMS` and
  `tools/fetch.sh` pin this one.
- `NOTICES-windows-x64.md`: the Windows zip's notices, also as a plain file.
- `libazahar-py-core-build-v1.2.0.tar.gz`: the build files for the Windows core.
- `mingw-w64-runtime-source.tar`: the source of the compiler runtime parts linked into the Windows core.
- `SOURCE.md`: maps each binary to its source.
- `SHA256SUMS`: sha256 of every other asset.

## Licence and source

Both core binaries are GPLv3. Their complete corresponding source is on this page: the Azahar source asset, the OpenSSL
source tarball, the system-archive generator snapshot, both build-files assets, the compiler runtime source, and this
repository at the tag. The Windows core links OpenSSL (Apache-2.0) statically; its runtime parts keep their own
licences, listed in `NOTICES-windows-x64.md`.

## Homebrew only

Homebrew only: no ROMs, no console keys, no Nintendo certificates and no Nintendo system files are included or needed by the tests; our core is built
without Azahar's built-in key data and default HTTP client certificate, and it loads no keys.

## Install

See the README, which has macOS and Windows steps. On macOS, macOS 15 or later is required.
