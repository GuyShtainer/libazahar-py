# Phase 7 IP and legal consult: the licence delta for v1.1.0 (ip-legal, 2026-11-17)

Consult for Phase 7 (item laz-703, step W1b). It covers only what v1.1.0 adds to v1.0.0, which was audited
shippable: a Windows x86-64 core DLL built in GitHub CI from source, a host that Windows users build themselves, and
seven assets carried over from v1.0.0 byte for byte.

Read: `docs/plans/phase-7.md` (section 4 and decisions D4, D5, D13), `docs/reviews/release-ip-legal.md` (the v1.0.0
consult), the v1.0.0 audit, `NOTICES.md`, `core/OPENSSL.md`, `docs/reviews/phase-7-diff-review.md` and the toolkit IP
knowledge base. The phase-7 branches do not yet hold the CI workflow or the Windows notices generator, so this consult
answers the plan, not finished code. Nothing was built or run.

Primary sources checked: GCC's `COPYING.RUNTIME` (the Runtime Library Exception 3.1), mingw-w64's winpthreads
`COPYING` and `COPYING.MinGW-w64-runtime.txt`, the GPLv3 text (repo `LICENSE`), the source of
`actions/attest-build-provenance`'s provenance builder, Sigstore Fulcio's certificate-extension list, GitHub's
attestation docs, and Microsoft's trademark guidelines.

**Not legal advice.** I am not a lawyer. Grades follow the house policy: RED (never ship), YELLOW (defensible, the
maintainer signs off), GREEN. Each claim carries a label: *settled text*, *persuasive reading*, *enforcement pattern*,
*house rule* or *unresolved*.

## 1. The static toolchain runtime: libstdc++, libgcc, winpthreads and the mingw-w64 CRT

### 1a. Is the source tar needed?

**libstdc++ and libgcc** are GPLv3 with the GCC Runtime Library Exception 3.1 *(settled text)*. Its section 1 says:
"You have permission to propagate a work of Target Code formed by combining the Runtime Library with Independent
Modules, even if such propagation would otherwise violate the terms of GPLv3, provided that all Target Code was
generated by Eligible Compilation Processes. You may then convey such a combination under terms of your choice".
- Every object in the DLL is compiled from source by GCC (Azahar, OpenSSL and the patches), so the condition holds.
  GCC's LTO is still GCC.
- So these two libraries put no source duty and no notice duty on us.
- The same holds for libgomp and libatomic, if they are linked; they carry the same exception.

**Our own GPLv3, as it reaches the whole DLL** *(persuasive reading, never tested in court)*: GPLv3 section 1 leaves
"System Libraries" out of Corresponding Source. A System Library is anything "included in the normal form of
packaging a Major Component", where a Major Component includes "a compiler used to produce the work", and which
"serves only to enable use of the work with that Major Component, or to implement a Standard Interface for which an
implementation is available to the public in source code form".
- libgcc is the compiler's own support library. libstdc++ implements ISO C++, winpthreads implements POSIX threads,
  and the CRT implements ISO C. All four ship with the mingw-w64 GCC toolchain, and all four have public source.
- So all four are very likely System Libraries, and outside the Corresponding Source we owe.
- This works because we convey the core under **GPLv3 only**. GPLv2's equivalent clause excludes a component that
  "accompanies the executable", which a static link arguably does. Keep conveying the binary under GPLv3 only, as
  the v1.0.0 consult already says.

**winpthreads and the CRT under their own licences** *(settled text)*: these licences are permissive (MIT, BSD-style,
public domain and similar). None of them asks for source.

**The one exception: libquadmath.** It is LGPL-2.1, not under the Runtime Library Exception. Some libstdc++ builds
use it for 128-bit floating-point conversions. If it is in the link:
- its source is owed, and that source is in the GCC tarball D13 already packs;
- NOTICES must carry the LGPL-2.1 text.
The same check covers libssp. Which archives the link actually pulls is a fact for the build, not a legal question.

**Verdict: the tar is not needed on the current reading, but keep it.**
- It costs one asset.
- It closes the "System Library" question without our having to win the argument.
- It covers libquadmath if it turns out to be linked.
- It matches D13's plan: "dropped only if W1b and W8 both say it is not needed". W1b does not ask to drop it.

**Actions for W2b1 and W8:**
- Record which archive members the link pulls: a linker map (`-Wl,-Map=`) or `-Wl,--trace`. Keep it in build.inputs
  or beside it. The `linkLibs.rsp` list does not show the libraries g++ adds by itself.
- If libquadmath, or any other archive that is neither under the Runtime Library Exception nor permissive, appears,
  the tar becomes needed. Add that archive's licence text to NOTICES.
- SOURCE.md describes the tar truthfully: "the Ubuntu source packages of the toolchain runtime linked into the DLL;
  build.inputs maps each compiler ident in the DLL to its package". Claim a match only for idents that D13's mapping
  proves.
  - A second compiler ident is expected: the CRT and winpthreads archives keep the ident of the compiler Ubuntu built
    them with.

### 1b. Is more than the NOTICES text needed?

Yes, but only inside NOTICES. Section 4 of the plan summarises the runtime as "winpthreads MIT-style; mingw-w64 CRT
ZPL and public domain". The licence files themselves ask for more *(settled text, mingw-w64 master, 2026-11-17)*:
- **winpthreads `COPYING`** holds two licences:
  - an MIT licence from the mingw-w64 project ("shall be included in all copies or substantial portions");
  - a BSD-3-style licence from Lockless Inc., for derived parts: "Redistributions in binary form must reproduce the
    above copyright notice, this list of conditions and the following disclaimer in the documentation".
- **`COPYING.MinGW-w64-runtime.txt`** holds several blocks:
  - the mingw-w64 project's own notice, and the NetBSD getopt code, both with the same binary-reproduction clause;
  - gdtoa (David M. Gay and Lucent), which asks for the notice "in supporting documentation";
  - Todd C. Miller's getopt and Rich Felker's MIT code, which ask for the notice "in all copies";
  - Sun and Cephes maths code;
  - Wine headers under LGPL-2.1. These are headers only. Their compiled-in remains are GUIDs, layouts and small
    inline functions, which LGPL-2.1 section 5 leaves unrestricted *(persuasive reading)*.
  - The file's contents vary by version: older versions name ZPL 2.1.

**Action:** the Windows NOTICES, both inside the zip and as the loose `NOTICES-windows-x64.md`, carries both files
verbatim.
- Take them from the source package version actually linked, unpacked from D13's tar, and not from mingw-w64 master
  or memory.
- Make the asset table's licence column say "see NOTICES" instead of a summary that may not match.
- The Runtime Library Exception asks for no notice. A NOTICES line naming libstdc++ and libgcc as "GPLv3 with the GCC
  Runtime Library Exception 3.1" is courtesy, and it is right to keep it.

## 2. OpenSSL 3.6.5 on Windows

**No legal difference from the Mac core.** The v1.0.0 analysis carries over unchanged: Apache-2.0 into GPLv3 is
compatible one way *(settled: both FSF and ASF say so)*, and the section 4 duties are as follows.
- **4(a), a copy of the licence:** the Apache-2.0 text and the line "The OpenSSL Project Authors" go inside the
  Windows zip's NOTICES.
- **4(b), notices in modified files:** we modify no OpenSSL file.
- **4(c), notices in redistributed source:** the source asset is the same byte-identical tarball.
- **4(d), NOTICE:** the tag has no NOTICE file, so nothing is owed.

What changes is only the provenance, and D5 already covers it.
- The libraries are built by us in CI, not taken from a Homebrew bottle. So the "scripts used to control compilation"
  (GPLv3 section 1) are the Configure line and the workflow.
  - D5 records the Configure line in build.inputs.
  - `.github/workflows/core-win64.yml` and `tools/build-core-win64.sh` are members of the v1.1.0 build-files asset.
- OpenSSL on Windows links only Windows system DLLs (bcrypt, CRYPT32, WS2_32, ADVAPI32, USER32). These are System
  Libraries, so nothing is owed for them.
- The OPENSSLDIR compiled in, `C:/Program Files/Common Files/SSL`, is neutral. It holds no username or local path,
  and it is OpenSSL's own recommended Windows default.

**Action: none beyond D5.** `core/OPENSSL.md`'s Windows section should record:
- the Configure line;
- the compiler and its version;
- the sha256 of `libssl.a` and `libcrypto.a`;
- `openssl_src_sha256`.

## 3. `vulkan-1.dll`

**No notice is needed.**
- Licence duties attach to distribution. We distribute no Vulkan binary.
- The loader the host opens from System32 is installed by the user's graphics driver. That makes it an operating
  system component, a System Library under GPLv3.
- The core DLL does not import it; the core gets Vulkan through the host.
- The loader is Apache-2.0 in any case.
- The Vulkan headers compiled into the core already have their entry in NOTICES (Apache-2.0 OR MIT). The Windows
  notices generator must keep it.

**Action (truthfulness, not law):**
- The Mac NOTICES ends with a sentence about MoltenVK being fetched by `tools/fetch.sh`. That is false for Windows.
  The Windows NOTICES should say instead that the Vulkan loader, `vulkan-1.dll`, comes with the graphics driver and
  is not shipped.
- Standing tripwire: never ship `vulkan-1.dll`, a driver ICD or Mesa's dzn. Any of them would need notices and a fresh
  consult.

## 4. MSYS2's zlib in the host the user builds

**Nothing is owed.**
- We do not distribute the host, and a user who builds it for their own use conveys nothing *(settled text: GPLv3
  section 2 gives unlimited permission to run, and duties arise on conveying)*.
- zlib's licence has no binary-notice clause anyway. It forbids misrepresentation, requires marking altered source,
  and requires keeping the notice in source.
- Telling users to install MSYS2 packages creates no duty.

**Action: none.**

**Tripwire:** the moment a built host reaches anyone else, through a release asset or a CI artifact, it is
distribution. For a public repo, an Actions artifact can be downloaded by any signed-in GitHub user.
- That binary would then need notices for zlib, MSYS2's static winpthreads and CRT, and libgcc, and it would need an
  audit.
- So `test-windows.yml` uploads test reports only, never `azhost.exe` or `libazhost.dll`.

## 6. "Windows", "NVIDIA" and "RTX 3060" as tested-on facts

**Law** *(persuasive, consistent across our jurisdictions)*: naming another company's product to state a fact about
compatibility is nominative use.
- US: *New Kids on the Block* and *Toyota v. Tabari*.
- EU: Trade Mark Directive 2015/2436 Art. 14(1)(c), with *Gillette v LA-Laboratories* (C-228/03), the leading
  "compatible with" case.
- Israel: Trade Marks Ordinance s.47.
- Japan: Trademark Act Art. 26, which excludes use that is not "use as a trademark".

The conditions are the same in each: use only as much of the mark as needed, use no logo, and imply no sponsorship.
No law requires a ® symbol or an attribution line from a non-owner. *Enforcement pattern:* compatibility lines like
these are universal in open-source READMEs.

**House wording rule** (cheap, and it keeps us inside every version of the test):
1. **Plain text, factual, past tense:** "Tested on Windows 10 (64-bit) with an NVIDIA GeForce RTX 3060". Use the full
   correct product name on first use.
2. **No logos, badges or icons** for Windows, NVIDIA, GeForce or Vulkan.
3. **No endorsement words:** never "for Windows", "certified", "optimized for", "official", "supports all RTX". Prefer
   "runs on" and "tested on". Name the tested hardware as the hardware that was tested, not as a requirement unless
   it is one.
4. **The marks are never part of our own names.** That covers the project, the tool, the repo and any command.
   - The platform token in an asset file name (`windows-x64`) is descriptive and normal practice.
5. **One trademark footnote line** in the README, beside the existing non-affiliation line. For example: "Windows is
   a trademark of the Microsoft group of companies. NVIDIA, GeForce and RTX are trademarks of NVIDIA Corporation.
   Vulkan is a trademark of the Khronos Group. They are named here only to say what this was tested on; this project
   is not affiliated with or endorsed by them."
   - Microsoft's own guidelines ask for such a footnote. It is courtesy, not law.
6. **No speed or performance claims about the hardware** (an existing house rule). No "Vulkan conformant" claim
   either, since conformance is a Khronos programme.

## 7. GitHub's build attestation

**No privacy issue and no legal issue.**

**What it holds** *(fact, read from `actions/toolkit`'s `packages/attest/src/provenance.ts` and Fulcio's
`docs/oid-info.md`, 2026-11-17)*:
- the workflow's repository, path and ref;
- the event name (`workflow_dispatch`), the repository's and owner's numeric ids, and the runner environment;
- the commit sha and the run's URL;
- the subject: the DLL's file name and sha256.

The signing certificate carries the same identity fields. Neither holds the user who triggered the run, an email
address, or any file contents. The account name appears only as part of the repository URL, which is public anyway.
The run page shows who started the run, but GitHub already shows that for every run on a public repo.

**Permanence:**
- For a public repo, the attestation is also written to Sigstore's public-good Rekor transparency log, which cannot be
  edited or deleted. GitHub's own copy can be deleted.
- So the repo name, the commit sha and the DLL's digest become a permanent public record.
- It records a digest, not bytes, so it can never redistribute anything.
- Legally it helps: it is signed evidence that the binary was built from the public source by the public workflow.
  That is exactly the provenance claim our key-free build makes.

**Actions:**
1. Attest only a commit on main that has passed the pre-push checks, and only after job 1's key search has passed.
   That is the D4 order already. A Rekor entry naming a commit cannot be removed by a later history rewrite, and after
   the push no rewrite is possible anyway.
2. Give `id-token: write` and `attestations: write` to the attest step's job only, or to a small job that downloads
   the artifact and attests it. Then a compromised build dependency cannot mint a signing token in the build job.
   This is security hygiene, not law.
3. If job 3's leak check ever fails: delete the artifact and the run's logs at once, and delete the GitHub-side
   attestation. The Rekor digest that remains is harmless.
4. Note for a future rename: the old name stays in Rekor. The v1.0.0 consult rates the name a courtesy risk, so this
   is acceptable.

## Left open

- Whether libquadmath, libssp or libatomic is linked. The link map settles it.
- The exact runtime licence texts depend on the mingw-w64 version Ubuntu ships in the pinned image.
- Encryption export rules (US EAR 742.15(b); Israel's encryption order) were not researched in this consult or in
  the v1.0.0 one. They are not a Windows delta: the Mac core links the same OpenSSL. *Unresolved, low.*
